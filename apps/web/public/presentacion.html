06 / TRAZABILIDAD

Comentarios e historial

Cada acción relevante pasa por un permiso, una validación Zod compartida y al menos una prueba.

05 / REGLAS DEL SISTEMA

Los permisos no se improvisan.

El rol vive en ProjectMember: la misma persona puede ser OWNER en un proyecto y VIEWER en otro. Ningún endpoint decide permisos por su cuenta.

ACCIÓN OWNER MEMBER VIEWER
// packages/shared/src/permissions.ts export function can(role, permission) { if (!role) return false; // no miembro return MATRIX[role].has(permission); } // API: protege la ruta // Web: oculta el botón que igual fallaría

El test de tabla declara la matriz esperada de forma independiente: si alguien afloja un permiso, la prueba lo delata en vez de seguirlo.

07 / PRUEBAS QUE CAMBIARON DECISIONES

La prueba no solo verifica.
También descubre.

Seis casos reales del repositorio: el nombre de la prueba y lo que obligó a cambiar.

CONCURRENCIA

Referencias sin colisión

asigna referencias distintas en dos creaciones simultáneas

UPDATE itemCounter + 1 y el INSERT en la misma transacción
ROLLBACK

Historial atómico

revierte el cambio de estado si PostgreSQL falla al registrar el historial

cambio + ActivityLog: o se guardan los dos o ninguno
TRAZABILIDAD

Ediciones simultáneas

serializa dos ediciones concurrentes sin fromValue obsoleto

aislamiento Serializable + reintento ante P2034
DEADLOCK

Comentar vs. borrar

Un FOR UPDATE en el comentario podía bloquearse contra el borrado del mismo elemento.

FOR KEY SHARE: frena el borrado, no las ediciones
CACHÉ

Tablero sin datos viejos

Editar, borrar o quitar un miembro debe refrescar el tablero de ese proyecto, y no el de otros.

invalidación dirigida por projectId
UX

Arrastre optimista

si el servidor rechaza el cambio, la tarjeta regresa a su columna y se informa

actualización optimista con rollback en TanStack Query
08 / ZOOM TÉCNICO

Dos PATCH al mismo tiempo. ¿Qué dice el historial?

Reproduce la prueba dos PATCH concurrentes dejan una bitácora encadenada: el proyecto se llama «Mira»; A lo renombra «Alfa» y B, «Beta».

PATCH A · «Alfa»
PostgreSQL · fila del proyecto
PATCH B · «Beta»
ActivityLog · PROJECT_UPDATED
# fromValue toValue
vacío

En elementos de trabajo la misma propiedad se protege con aislamiento Serializable y hasta tres intentos; en comentarios, con FOR KEY SHARE.

11 / LA DECISIÓN QUE NO SE VE

Un rewrite que salva el login en Safari.

vercel.app y onrender.com están en la Public Suffix List: si el navegador hablara directo con Render, la cookie de sesión sería de terceros.

✗ Cross-site

mira-pds.vercel.app→mira-api-2epf.onrender.com
🍪 Cookie de terceros con SameSite=None. El login parece funcionar y luego todo responde 401.
Safari ITP · bloqueaChrome incógnito · bloqueaFirefox · particiona

✓ Mismo origen

mira-pds.vercel.app/api/*→ Vercel reenvía →Render
🍪 Cookie first-party HttpOnly; Secure; SameSite=Lax. Además, Lax impide que otro sitio dispare peticiones con la sesión (CSRF).

12 / INFRAESTRUCTURA COMO CÓDIGO

Un deploy que no puede romper la demo.

Todo lo que no es secreto vive en render.yaml y vercel.json, versionado y revisado en un PR. Así construye Render cada push a main:

01npm ci--include=dev · monorepo completo
02Build APItsup
03Migrarprisma migrate deploy
04Seedidempotente · usuarios demo
05Health/api/health/live
06Tráficorecién ahí cambia la versión

SI UNA MIGRACIÓN FALLA → FALLA EL BUILD → LA VERSIÓN ANTERIOR SIGUE ATENDIENDO

LIVENESS VS. SALUD

Dos health checks

Render mira /live, sin base: un parpadeo de Supabase no reinicia una API sana. El pinger mira /api/health: SELECT 1 con tope de 2 s y 503 si no responde.

MIGRACIONES

Expand / contract

Corren contra producción mientras la versión anterior atiende. Borrar una columna toma dos releases.

SECRETOS

Fuera del repo

sync: false para las URLs de la base; JWT_SECRET lo genera Render. buildFilter: un cambio solo del front no redespliega la API.

IPv6

Lo que costó aprender

La conexión directa de Supabase es solo IPv6 y Render no sale por IPv6: las migraciones usan el session pooler.

14 / REFLEXIÓN

Las pruebas cambiaron cómo construimos.

La arquitectura y la forma de integrar evolucionaron a partir de los defectos encontrados.

01

Diseñar para probar

Repositorios inyectables y contratos compartidos permiten probar cada regla en milisegundos, sin base de datos.

02

Integrar también es probar

Una feature correcta puede romper otra por caché, rutas o archivos compartidos. Por eso hay pruebas de invalidación entre vistas.

03

La concurrencia no se ve en una demo

Solo aparece con dos peticiones simultáneas. Las pruebas encontraron lecturas obsoletas y hasta un deadlock antes que un usuario.

04

Desplegar también tiene pruebas

Los health checks están cubiertos por integración, y el build se detiene si una migración no aplica.

Probar temprano nos obligó a hacer explícitas reglas que habrían quedado implícitas.
